# Context Compaction 第四阶段：真实环境集成验证

## 范围与记录

本阶段没有改变 LangGraph Checkpoint、业务工具或历史评测数据。合成样本见 [`dataset-v1.json`](../../data/evaluation/context-compaction-v2/dataset-v1.json)，逐题离线结果见 [`offline-results.json`](../../data/evaluation/context-compaction-v2/offline-results.json)，真实 Redis 协议测试记录见 [`redis-integration-results.json`](../../data/evaluation/context-compaction-v2/redis-integration-results.json)。样本由项目维护者编写，订单号均为合成标识；两组样本不代表生产对话分布。

## 独立 Redis 集成

Windows 环境没有 Docker/WSL Redis 服务，因此在项目临时目录运行独立的 **Memurai Developer 4.1.2** Redis 兼容实例，绑定 `127.0.0.1:16379`，报告的协议版本为 Redis 7.2.5。它不是官方 Linux Redis 容器。集成测试使用独立随机 owner/thread 和临时 SQLite 文件，不连接业务数据；测试后清理会话键。启用 AOF 后实际停止并重新启动服务，`verify_compaction_redis_restart.py` 在新进程中确认摘要和游标仍存在，随后删除测试键。

`ORDERCARE_TEST_REDIS_URL=redis://127.0.0.1:16379/0` 时运行 `uv run pytest -q tests/service/test_compaction_redis_integration.py`，结果 **3 通过**。覆盖新客户端读取、真实服务重启、Lua CAS 拒绝陈旧游标、6 次并发仅 1 次写入、重复压缩、不同 owner 隔离、写入中断后的错误抛出及恢复、敏感数字脱敏、超长用户内容跳过、TTL。未设置该环境变量时专项测试自动跳过，避免触碰业务 Redis。

测试发现 Redis Lua `cjson` 会把空数组编码为 `{}`。`LayeredMemory.session` 现在仅对 compaction 摘要中的空对象恢复为 `[]`，避免重启后摘要字段类型改变。该问题由真实服务测试发现并覆盖。服务重启验证了 Redis **AOF** 持久化；普通会话内存快照和 LangGraph Checkpoint 没有被替换。

固定样本还发现两项已有压缩器缺陷：自由文本中的“银行卡”可能进入摘要，现对含付款方式、卡号和支付账户等表述的整条用户消息跳过，避免部分脱敏遗漏；相同的 AI 回复文本可能让旧的纯内容游标匹配到更晚消息并跳过未处理历史。新游标绑定消息位置与指纹，旧游标采用最早匹配并允许安全重复处理。对应回归测试覆盖支付信息排除与旧游标升级。

## 离线摘要与 Token 分账

运行 `PYTHONPATH=src uv run python scripts/evaluate_compaction_phase4.py`。使用当前保守字符估算器和**压力测试配置**：Context Manager 总预算 900、Memory 400，压缩触发计算使用总预算 350、摘要上限 1200，以便短合成对话触发压缩；这不是生产默认配置。无真实 API 调用。**“保留”有两个层次：摘要存储含有字段，模型上下文真正收到字段。**

| 固定样本 | 原始消息 | 仅动态裁剪 | 裁剪 + 压缩摘要 | 摘要字段保留 | 模型可见字段 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 条件维修 | 560 | 301 | 301 | 4/4 | 2/4 |
| 退款与工单 | 478 | 317 | 697 | 4/4 | 4/4 |
| 合计 | 1038 | 618 | 998 | 8/8 | 6/8 |

动态裁剪单独节省 `(1038-618)/1038 = 40.46%`；压缩在这组样本中**额外增加 380 个估算 Token**，但把模型可见标注字段从仅裁剪时的部分历史提高到 6/8。第一组摘要因超过 Memory 预算被整段跳过；第二组摘要进入了模型上下文，保留 4/4 字段。8/8 是 **Redis 摘要字段**保留率，不是模型事实保留率。当前请求与系统规则均保留，但不能据此宣称跨轮任务连续性已达到验收。两组样本的摘录耗时分别为 1.526 ms 和 0.311 ms，仅是本地离线运行时间，API 成本为 ¥0。压缩前后没有真实模型 Token 计数；上述数字只是同一估算器下的对比。

该结果揭示集成瓶颈：当前压缩器保存结构化历史，却没有保证摘要在 Context Manager 预算内进入模型视图；即使进入视图，也可能增加 Token，而不是节省 Token。后续应在不丢关键约束的前提下设计摘要字段优先级和预算内选择，再用更多长对话及真实任务验证。此阶段不改变已有上下文组装策略，以免把验证工作混入新功能开发。

## 真实 DeepSeek 摘要验收

用户批准后，在固定两组样本上**恰好调用 6 次**，每组依次为首段摘要、增量合并、基于摘要回答当前问题。模型返回的 `model_name` 六次均为 `deepseek-flash`，temperature 0，六次 `finish_reason` 均为 `stop`；没有重试、Mock/Ollama 回退或额外 Judge 请求。完整原始响应、解析 JSON、各次 usage 与耗时保存在 [`llm-results.json`](../../data/evaluation/context-compaction-v2/llm-results.json)，逐题语义核验在 [`human-review.json`](../../data/evaluation/context-compaction-v2/human-review.json)。两者分别保留模型原始记录与单人复核结论；复核不是独立盲评。

| 样本 | 首段摘要 | 增量摘要 | 摘要后续答 | 人工语义字段保留 | 续答约束 | 观察到实质编造 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| 条件维修 | 289 入 / 146 出 | 359 入 / 189 出 | 263 入 / 61 出 | 4/4 | 保留先核验资格、不得直接建工单、不能退才谈维修 | 未见 |
| 退款与工单 | 255 入 / 132 出 | 327 入 / 156 出 | 236 入 / 54 出 | 4/4 | 保留先核验资格、不能退才考虑工单、敏感操作需确认 | 未见 |

总 usage 为 **1729 输入、738 输出 Token**，六次耗时合计 **7.172 秒**；其中四次摘要耗时 **5.349 秒**，两次基于摘要续答耗时 **1.823 秒**。按 [DeepSeek 官方价格表](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)的缓存未命中峰时费率估算约 **¥0.009362**（非峰时约 ¥0.004681），不是账单金额。原预算为峰时约 ¥0.05136；实际 usage 远低于预算。输出文件未包含合成手机号后四位、付款方式或 API Key。

单人复核认为两次增量摘要均忠实保留前段关键事实，合计 **8/8** 条人工标注事实在摘要中可找到，两个续答都保持了必要的条件顺序与审批约束；未观察到确定性的资格捏造、工单或退款“已执行”的虚构。自动字面匹配只命中部分字段，因为模型将 `source#章节` 改写成 `source《章节》`、将条件句同义改写；语义结论有逐题理由可查。第一题的政策证据未给出具体维修步骤，模型也没有列出虚构步骤，但其“以后引用该政策说明维修步骤”的措辞仍需实际政策核验。这里的 **2/2** 仅是合成对话的**回答层连续性**，没有运行真实工具、LangGraph 长任务或人工审批；不能外推到线上任务完成率。

### 三种上下文方案的比较

[`three-context-comparison.json`](../../data/evaluation/context-compaction-v2/three-context-comparison.json) 使用同一固定样本、上述**压力预算**和同一保守估算器，对模型实际可接收的上下文重新组装；**只有评测脚本直接给摘要的续答调用了真实模型**。原始和仅裁剪方案没有在六次预算内调用模型生成答案，故三方案的回答正确率不能作真实 A/B 比较。

| 两题合计（压力预算） | 原始上下文 | 仅动态裁剪 | 裁剪 + 现有摘录摘要 | 裁剪 + DeepSeek 摘要 |
| --- | ---: | ---: | ---: | ---: |
| 模型视图估算 Token | 1038 | 618 | 998 | 618 |
| 摘要是否进入模型视图 | 不适用 | 不适用 | 1/2 | 0/2 |
| 标注事实模型可见（人工核对） | 8/8 | 4/8 | 6/8 | 4/8 |

DeepSeek 两份最终摘要本身估算为 **521 + 467 = 988 Token**，均超过此实验的 Memory 注入预算 400，故 Context Manager 把它们整段跳过。真实模型的两次续答是评测脚本**直接提供摘要**所得，不能被误认为线上组装链也能取得同样效果。现有摘录式摘要在一题中增加 380 个估算 Token，换来更多可见事实；没有实现额外 Token 节省。动态裁剪的 40.46% 节省与压缩无关。

生产默认配置为总预算 4096、80% 触发阈值、摘要上限 384。两组原始输入分别仅 560 和 478 估算 Token，**默认配置下均不会触发压缩**；两份实验性 DeepSeek 摘要也都超过默认摘要上限 384。因而本阶段的模型结果是受控压力实验，不是默认线上负载的直接效果数据。

**结论：当前实验没有证明压缩带来线上收益，不建议默认启用或改为 LLM 摘要。** 模型能在直接给定摘要时续接两组任务，但压力预算下 LLM 摘要 0/2 注入；默认生产预算下这两题又根本不会触发压缩。现有摘录摘要在压力实验中改善可见事实，但增加 Token；LLM 摘要还增加 API 延迟与费用。继续保持现有线上策略不变；若后续获批开发，应先解决摘要预算内选择与去重，再用更长、更多样本做独立留出集和端到端任务验证。本次实验到此停止，不自动进行下一轮 API 调用。
