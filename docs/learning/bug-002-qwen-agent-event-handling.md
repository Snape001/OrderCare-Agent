# Bug 002：Qwen Agent 接入后服务事件处理错误

记录日期：2026-07-03  
发现方式：真实 FastAPI 集成测试  
状态：已修复并增加回归测试

## 1. 背景

独立脚本已经跑通以下 Function Calling 流程：

```text
Qwen 选择 get_order_status
→ Python 查询 SQLite
→ 将工具结果交回 Qwen
→ Qwen 生成最终订单回答
```

将相同能力接入 FastAPI 和 LangGraph 后，真实 HTTP 请求暴露出两个事件处理问题。

## 2. 问题一：正常请求返回 500

### 现象

请求订单状态时，模型和工具实际已经执行，但接口返回：

```text
HTTP 500 Unexpected error
```

日志记录：

```text
Unexpected response type: updates
```

### 根因

LangGraph 在一次 Agent 运行中会产生多种事件：

```text
updates：节点增量更新
values：当前完整状态
messages：消息或流式 Token
```

旧服务只读取事件列表的最后一项，并假设它一定是 `values`。Qwen工具调用图的最后一项
可能是普通 `updates`，因此被误判为异常。

### 修复

服务不再依赖最后一个事件，而是从事件中寻找真正的最终 `values`；如果本轮发生审批
中断，则优先处理 `__interrupt__`。

修复后，真实订单查询返回 HTTP 200：

```text
订单：ORD1001
商品：无线耳机
状态：运输中
签收情况：未签收
```

## 3. 问题二：工单审批提示被普通回复覆盖

### 现象

用户请求创建工单时，LangChain已经产生人工审批中断，但接口只返回：

```text
我将为您创建物流异常工单。
```

用户看不到“确认/取消”提示，无法完成审批。

### 根因

同一次运行中，模型普通消息、完整状态和审批中断都会产生事件。服务从后往前找到了一条
普通 `values`，却没有优先检查整轮是否出现 `__interrupt__`。

### 修复

先扫描整轮事件：

1. 只要存在 `__interrupt__`，优先返回结构化审批请求。
2. 没有中断时，才返回最后一个完整 `values`。
3. 用户回复“确认”时转换为 `approve`。
4. 其他回复转换为 `reject`，写操作默认不执行。

真实接口返回：

```text
即将执行以下写操作：
create_support_ticket：{订单号、手机号后四位、分类、摘要}

请回复“确认”执行，或回复“取消”。
```

确认后才生成本地工单编号。

## 4. 防护措施

正式Agent对创建工单设置了三层保护：

1. Prompt要求写操作前确认。
2. 工单工具再次验证手机号后四位。
3. Human-in-the-loop中间件在执行工具前硬性中断。

Prompt属于模型约束，后两层属于程序约束。即使模型没有遵守Prompt，程序仍不会直接执行
未经批准的写操作。

## 5. 回归测试

新增测试覆盖：

- 只读订单工具可以自动执行。
- 创建工单会产生审批中断。
- 回复“确认”后才执行工具。
- 非明确确认会拒绝写操作。
- 审批中断后即使还有普通状态事件，也必须优先返回审批提示。

## 6. 面试表达

> 在将Qwen Function Calling接入FastAPI时，独立脚本正常但接口返回500。我通过日志定位
> 到LangGraph会同时产生updates、values和interrupt事件，旧服务错误地假设最后一条事件
> 就是最终结果。修复事件选择后，又发现工单审批中断会被普通回复覆盖，因此将审批事件
> 设置为最高优先级，并把用户的确认/取消转换为结构化approve/reject决策。最终跑通了
> 订单查询、RAG政策回答和工单人工审批三条真实HTTP链路。
