# Bug 001：发票政策问题被错误路由到订单查询

记录日期：2026-07-03  
发现方式：手工验收  
状态：已修复并增加回归测试

## 1. 问题现象

在知识库中把发票申请期限从 30 天修改为 45 天后，输入：

```text
订单完成40天后还能申请电子发票吗？
```

系统没有返回发票政策，而是回答：

```text
请提供订单号，例如 ORD1002。
```

## 2. 预期结果

这是一个通用政策问题，不需要查询某一笔真实订单。系统应该进入 RAG
知识库检索并返回：

```text
发票服务
订单完成后 45 天内可以申请电子发票。
```

## 3. 根因分析

Agent 的意图判断按代码顺序执行。原来的订单判断条件过于宽泛：

```python
if order_id or any(word in text for word in ("订单", "退款资格", "能退款")):
```

只要用户的问题中出现“订单”两个字，就会提前进入订单查询分支。
因此，后面的“发票”政策检索分支没有机会执行。

这类问题可以概括为：

> 前面的宽泛路由条件截胡了后面的正确意图。

## 4. 修复方案

将订单意图缩小为明确的订单操作表达：

```python
order_intent_words = ("查询订单", "查订单", "订单状态", "退款资格", "能退款")
if order_id or any(word in text for word in order_intent_words):
```

修复后的路由规则：

- 包含 `ORD1001` 这类真实订单号，或者明确说“查询订单”“订单状态”：
  进入订单工具。
- 包含“发票”“开票”“补票”“报销”等政策表达：
  进入 RAG 知识库。

## 5. 回归测试

新增自动测试：

```python
async def test_policy_question_with_order_word_is_not_misrouted():
    result = await customer_support_node(
        {"messages": [HumanMessage(content="订单完成40天后还能申请电子发票吗？")]}
    )

    answer = result["messages"][-1].content
    assert "发票服务" in answer
    assert "45 天" in answer
    assert "请提供订单号" not in answer
```

同时将该问题加入 HTTP 端到端验收，保证从 FastAPI 接口进入时也能得到正确答案。

修复后的验证结果：

```text
客服业务与 RAG 单元测试：11 passed
HTTP 端到端验收：9/9 通过
```

## 6. 学到的知识点

1. 意图路由有执行顺序，前面的条件可能阻止后面的分支执行。
2. 关键词不能过于宽泛，“包含订单”不等于“查询具体订单”。
3. 手工测试发现的失败案例应该转成自动化回归测试。
4. 单元测试验证路由函数，端到端测试验证完整 API 请求链。
5. RAG 检索正确不代表整个应用一定正确，检索前的意图路由同样重要。

## 7. 面试表达

## 8. 后续优化

当前仍然使用显式规则进行意图路由。随着意图数量增加，关键词规则会越来越难维护。
后续接入真实 Qwen Agent 时，可以使用结构化输出或 Function Calling 选择工具，
同时保留这些测试用例验证新路由没有退化。
